Partner Guide

Add an accessible sign-up to your website with one script tag. Amharic and English, read aloud, voice answers, text size up to 400%, and it keeps working on a weak connection.

How to adopt Bridge

Bridge is a web component, <bridge-onboarding>, plus a REST API and schema.org JobPosting JSON-LD. Most partners only need steps 1 to 4.

  1. Prepare your settings. Fill in the form below: your organisation, the exact address (origin) of every site that will show the component, your help contacts and your languages.
  2. Send them to the Bridge operator. There is no self-service sign-up yet. The operator creates your partner in the database (the SQL tab shows the query) and confirms your partner key. The key works only after that. A new origin can take up to 2 minutes to be accepted.
  3. Add the component to your page. Copy the HTML snippet. Put the element where the form should appear, in a container with a sensible maximum width.
  4. Listen for events. bridge-onboarding:completed gives you the learner_id. No event ever contains names, phone numbers or support needs. See Events.
  5. Optional: read your learners from your server. Ask the operator for a client ID and secret, then use the partner server API (OAuth 2.0 client credentials, scope learners:read).
  6. Optional: show jobs with their accommodations. Read published jobs as JobPosting JSON-LD, with no key.

The first load can be slow. The hosted API runs on a free plan that sleeps when nobody uses it. The component retries reading requests for up to about 75 seconds and shows: "Connecting to the service. The first time, this can take up to a minute."

Before you go live

  1. Origins match exactly. https://www.your-site.example and https://your-site.example are different origins. A page from a missing origin gets 403 origin_not_allowed.
  2. Your page works over https. Voice answers need the microphone, which browsers allow only on https:// pages.
  3. Your Content-Security-Policy allows the component. See Styling and CSP.
  4. Don't redirect at once on completion. Let the person read the Done screen at their own pace.

Using the component

Load the script once per page (a classic script, not type="module"). One script can serve several <bridge-onboarding> elements. The element fills the width of its container.

Attributes

Attribute Values Default What it does
partner your partner key none Sent as X-Partner-Key on every API call. Required.
api the API origin, for example https://accessible-onboarding.vercel.app (no /api/v1) the same site as the page Where the component sends API calls. Set it whenever the API is not on your site.
flow signup, language, jobs, job-application, profile signup Which part to show (see below).
lang am or en (any language with a locale file) en The starting language, used only until the person chooses a language on this device.
simple bare simple or simple="true" off Starts in Simple mode.
manage-title "false" to turn off on Whether the component may set the page title, for example "Question 4 of 11: …". Turn it off on a busy page.
job-id a job's ID (UUID) none For flow="job-application": the job to apply for.

Set attributes in your HTML. flow, lang and simple are read once, at start.

Flows

flow What the person sees
signup The sign-up. The first time on a device, the language screen comes first (unless only one language is offered). A person who started on this device continues where they stopped. The Done screen offers "Find a job" and "See or change my details".
language The language screen first, every time, then the sign-up.
jobs Jobs with a "Support I need" filter, pre-filled with the needs given at sign-up on this device. Matching happens on the device.
job-application The application for job-id. Only a learner who finished signing up on this device can apply; anyone else is asked to sign up first.
profile "My profile": see, change or delete what is kept (for the sign-up made on this device).

The sign-up questions

One question per screen, in this order (some depend on earlier answers):

  1. Welcome, then consent to data use.
  2. Full name: your name, your father's name and your grandfather's name (one field).
  3. How can we reach you: phone, Telegram, through an organisation, or no way.
  4. Phone number (if phone or Telegram).
  5. Date of birth, in the Ethiopian or Gregorian calendar (optional).
  6. Sex (optional).
  7. Region or city (optional): the 12 regions, Addis Ababa, Dire Dawa, or outside Ethiopia.
  8. Highest education (optional).
  9. Which ID do you have: Fayda, Kebele ID, refugee ID, UNHCR proof, another document, or none.
  10. For another document: its type and an optional photo (stored encrypted). Then, optionally, the last 4 characters of the document.
  11. For no ID: which referral organisation can help, and how they can reach you.
  12. What would help you (supports), anything else, and who may see the supports.
  13. Check your answers, then Done.

Bridge does not verify identity. Identity is recorded as self_declared, or partner_attested when a referral organisation that met a person without ID vouches for them with a one-time code. The last 4 characters are an optional reference that helps staff match a document in person, not a check. Real Fayda verification (OTP or biometric authentication through the national ID programme, NIDP, as a licensed relying party) is on the roadmap, not built.

Events

Every event bubbles and is composed, so you can listen on the element or on document. detail never contains names, phone numbers or support needs; it may contain IDs.

Event When detail
bridge-onboarding:ready Once, when the component appears { "flow": "signup" }
bridge-onboarding:step-changed A new question shows (sign-up and job application) { "step": "phone", "index": 4, "total": 11 }
bridge-onboarding:saved An answer was saved on the device, or answers reached the server { "where": "device" } or { "where": "server" }
bridge-onboarding:support-requested The learner's support needs reached the server {}
bridge-onboarding:completed The sign-up was submitted { "registration_id": "…", "learner_id": "…" }
bridge-onboarding:application-submitted A job application was sent { "job_id": "…", "application_id": "…" }
bridge-onboarding:error The API refused something (not for being offline) { "code": "origin_not_allowed" } (an API error code)

What your learners get

The top bar

  • Get help shows your help phone and Telegram, with the buttons "Call support" (opens the phone's dialler with the number), "Send an SMS" and "Open Telegram".
  • Language (when you offer more than one) opens the language screen. Its globe icon marks it in any language, and read aloud also says "Language" in English.
  • Dark mode switches between light and dark colours.
  • Accessibility opens a panel with Read aloud, Answer by speaking, Text size (100% to 400%) and Simple mode, and a Close button. Escape also closes it.
  • Every label is in the language the learner chose.

Read aloud

  • On by default, because we can't know whether someone can see the screen. Browsers allow no sound before a key press or tap, so it starts at the first key press or tap.
  • It first reads the page from top to bottom: the top bar, then the screen, then "Press Tab to go from one item to the next."
  • After a Tab (or a tap), it describes the focused item. Fields say what they are and what to do, for example "Type your answer, then press Enter."
  • A learner's own answers are only ever read by the device's own voice, never sent to a server.

Voice answers

  • The first time, the person is asked whether their voice may be sent to a speech service.
  • What is heard goes straight into the field and is said back ("We heard: …"), with Say again and Type instead.
  • The microphone closes after one answer.

Offline

Every answer is saved on the device first, then sent. If the connection drops, answers wait on the phone and are sent when it comes back. The script itself must load once online.

Partner settings

Each partner has a JSON config in the partners table. GET /api/v1/config returns it, with defaults for anything missing. There is no settings page yet: ask the Bridge team and they change it for you (the SQL below is what they run).

Field Example Used by the component today?
languages ["am","en"] Yes: the languages offered. With one, the language screen is skipped.
help {"phone":"+251 11 123 4567","telegram":"@your_handle"} Yes: the "Get help" panel.
default_language "am" Yes: the starting language, unless your page sets lang or the learner already chose one.
id_routes ["fayda","kebele_id","none"] Yes: only these choices are offered at "Which ID do you have?".
theme {"primary":"#0b6e4f"} Yes: buttons and highlights in light mode, if the colour has at least 4.5:1 contrast on white.

Change the help phone and Telegram

SQL (operator): 
UPDATE partners
SET config = jsonb_set(config, '{help}', '{"phone":"+251 11 123 4567","telegram":"@your_handle"}')
WHERE publishable_key = 'pk_…';

Change the languages

SQL (operator): 
UPDATE partners
SET config = jsonb_set(config, '{languages}', '["am","en"]')
WHERE publishable_key = 'pk_…';

Add or remove an allowed origin

SQL (operator): 
UPDATE partners SET allowed_origins = array_append(allowed_origins, 'https://your-site.example')
WHERE publishable_key = 'pk_…';

UPDATE partners SET allowed_origins = array_remove(allowed_origins, 'https://your-site.example')
WHERE publishable_key = 'pk_…';

Settings are read on every request, so a change shows the next time the component loads. The browser permission (CORS) list of origins is reloaded every 2 minutes, so a new origin can take up to 2 minutes to work.

Adding a language

Amharic and English are complete today. Every language is built into the one component script that all partners load, so the Bridge team adds languages: you don't change any code.

  1. Ask the Bridge team for the language you need (for example Afaan Oromoo).
  2. Help with the translation if you can. A native speaker translates every text: your staff or ours. We never ship machine translation. Texts not translated yet show in English.
  3. We add it, check it and publish a new component. Your page keeps the same script tag: nothing to change.
  4. We switch it on for your site by adding it to your languages setting (see Partner settings). Only languages in that list appear on your language screen.

What a new language gets: all screen text once translated. Read aloud uses the phone's own voice for that language (our server voice is Amharic only). Answering by voice works where the browser supports the language (Chrome). Ethiopian month names show in English until they are translated.

What data your platform receives

  • In the browser (events): IDs only, such as learner_id and registration_id, plus step IDs and error codes. Never names, phone numbers, support needs or answers.
  • From the partner server API: only your own learners who finished signing up: learner ID, full name, preferred name (normally empty), language, status, identity level (self_declared or partner_attested), contact method, phone (if any) and whether it was verified (never, today), and the registration time.
  • Never shared with platforms: support needs, ID route, document type, document photo, last 4 characters, date of birth, sex, region, education, other answers, referrals and consents.
  • Employers see an applicant's support needs only when the learner attaches them to that application. Each read is audit-logged.
  • On the learner's device, under your site's origin: IndexedDB bridge-onboarding (session, waiting answers, a copy of the answers) and a few localStorage keys starting with bo: (language, read aloud, text size, speech consent). "Forget me on this phone" deletes them.

Full field lists are in the REST API docs.

Styling and Content-Security-Policy

  • The component draws inside its own shadow root. Your CSS can't break it, and its CSS can't touch your page.
  • It never changes your address, history, scroll position or styles, and never moves focus on first load. The only exception is the page title (turn it off with manage-title="false").
  • It loads no web fonts. If your users' phones lack an Ethiopic font, load Noto Sans Ethiopic on your page; the component will use it.

If your page sends a Content-Security-Policy header, allow:

Directive Add Why
script-src https://accessible-onboarding.vercel.app the component script
connect-src https://accessible-onboarding.vercel.app API calls
style-src 'unsafe-inline' the component puts a <style> in its shadow root
media-src https://accessible-onboarding.vercel.app, blob:, data: read-aloud audio

If you send a Permissions-Policy header, keep microphone=(self) for voice answers.

Local development

Only when you run Bridge on your own computer.

  • Development web server: http://localhost:5173. API: http://localhost:8080 (Swagger UI at /api/docs).
  • Use api="http://localhost:8080" on the element, or leave api empty on pages served by the development server (it forwards /api to the API).
  • The demo partner pk_demo_savanna from seed allows http://localhost:5173 and http://localhost:8081, among others. localhost and 127.0.0.1 are different origins.
  • npm run build:widget (in frontend/) writes dist-widget/bridge-onboarding.js if you want to host the script yourself.
