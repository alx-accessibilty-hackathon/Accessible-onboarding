Bridge Onboarding REST API

This is the reference for the Bridge REST API. The same API powers the accessible sign-up component <bridge-onboarding>, the career gateway, the staff app, and server-to-server integrations for partner platforms. To embed the component with one script tag, see the Partner Guide.

Browse every endpoint, status code and example, and try requests live.

Open Swagger UI ↗

Base URLs

  • API base: https://accessible-onboarding.vercel.app/api/v1 (the hosted site forwards /api, /health and /ns to the API server)
  • API server (direct): https://accessible-onboarding.onrender.com/api/v1
  • Health check: GET https://accessible-onboarding.vercel.app/health → {"status":"ok"}
  • Contract (OpenAPI 3.0.3): https://accessible-onboarding.vercel.app/api/openapi.yaml

JSON everywhere, with snake_case fields. Two exceptions: POST /oauth/token is form-encoded and POST /speech/transcriptions is multipart. IDs are UUIDs. Step IDs (full_name, phone…) and flow IDs (signup) are text. Times are RFC 3339 in UTC.

Three integration levels

Level What you do Where it is documented
1. Script tag Add one <script> and a <bridge-onboarding> element to your page. The component calls this API for you. Partner Guide
2. REST API Build your own sign-up screens on the REST API, and/or read the learners who signed up on your site from your server with OAuth 2.0. Sign-up, Partner server API
3. JobPosting JSON-LD Read every published job as schema.org JobPosting, with the accommodations each job offers. JobPosting JSON-LD

The first request can be slow.

The hosted API runs on a free plan that sleeps when nobody uses it. The first request after a quiet period can take up to about a minute. The component retries reading requests (GET) for up to about 75 seconds and tells the learner: "Connecting to the service. The first time, this can take up to a minute." In your own server code, use a generous timeout, or call GET /health first to wake the API.

Authentication & Callers

Each caller proves who it is in its own way:

Caller Send Get it from Lifetime
A website X-Partner-Key: pk_…. The browser also sends Origin, which must be on the partner's allowed list. the Bridge operator until changed
A learner X-Partner-Key and Authorization: Bearer lt_… POST /registrations or POST /resume/verify 30 days, renewed each time it is used
Staff (employers, partner staff) Authorization: Bearer st_… POST /auth/staff/login 12 hours
A partner's server Authorization: Bearer pt_… with the scope learners:read POST /oauth/token 1 hour
  • The partner key is public: it goes in your HTML. It is not a secret.
  • Tokens are opaque random strings (not JWTs). The server stores only their SHA-256 hash.
  • A learner token works only with the key of the partner the learner signed up with (403 forbidden otherwise).
  • Calls from curl or a server send no Origin header, so they skip the origin check. The partner key is still required.
  • If a page can't set headers, the partner key may also be sent as ?key= or ?partner_key=.

Errors

Every error has the same shape (except POST /oauth/token, which uses the OAuth shape {"error": "invalid_client"}): 

{
  "status": 422,
  "code": "validation_failed",
  "title": "Validation failed",
  "errors": [
    { "field": "value", "code": "phone_invalid" }
  ]
}

Program against code. title is a short English hint and may be missing. errors appears on 422.

Status Codes
400 invalid_request (unreadable body), invalid_id (an ID in the path is not a UUID)
401 partner_key_missing, partner_key_invalid, unauthorized (token missing, wrong kind, expired or revoked), resume_check_failed (with attempts_left)
403 origin_not_allowed, forbidden, insufficient_scope, consent_required
404 not_found (also for other people's things, so IDs can't be probed), resume_not_found
409 answer_conflict (with current), already_submitted, already_exists (applied twice), not_registered
410 resume_expired
413 payload_too_large (voice clip over 3 MB)
422 validation_failed with errors[]: required, too_short, too_long, invalid, invalid_choice, email_invalid, phone_invalid, date_invalid, digits_invalid, last4_invalid, file_invalid, file_too_large, unknown_question, unknown_step
429 rate_limited (with Retry-After), too_many_attempts
500 internal_error (details are logged, never sent)
503 speech_unavailable

Rate limits & Pagination

  • Rate limits (per API process): 120 requests a minute per IP, 1000 requests every 10 seconds for the whole server, and 20 a minute per IP on staff sign-in, OAuth tokens, starting a registration and resume lookup/verify. Over the limit you get 429 rate_limited and a Retry-After header in seconds.
  • Lists look like { "items": [...], "next_cursor": "…" | null }. Only GET /jobs pages today: pass next_cursor back as ?cursor= until it is null. Other lists return everything (or up to limit) with next_cursor: null.

Partner configuration

GET /api/v1/config X-Partner-Key

Returns the settings of the partner whose key was sent: languages, ID routes, the referral organisations a learner without ID can choose, the help contact, the theme colour and which speech services the server has. Missing settings get defaults.

The component uses languages, help and referral_partners today. It does not use default_language, id_routes, theme or speech yet. The settings are read on every request, so a change shows the next time the component loads. See Partner settings to change them.

Example request

curl -s -H "X-Partner-Key: pk_demo_savanna" \
  https://accessible-onboarding.vercel.app/api/v1/config

Example response (200)

{
  "partner": { "id": "7b6f1c2e-…", "name": "Savanna (demo)" },
  "languages": ["am", "en"],
  "default_language": "am",
  "id_routes": ["fayda", "kebele_id", "refugee_id", "unhcr_proof", "other_document", "none"],
  "referral_partners": [{ "id": "2c9e8f71-…", "name": "AAAPD" }],
  "help": { "phone": "+251 11 000 0000", "telegram": "@bridge_help_demo" },
  "theme": { "primary": "#cc3636" },
  "speech": { "server": true, "cloud_available": false }
}

Jobs

GET /api/v1/jobs X-Partner-Key

One page of published jobs, newest first, each with its accommodation codes. Matching jobs to a learner's needs happens in the browser, so needs are never sent here.

Query parameters

limit integer, 1–100 (default 20)
cursor the next_cursor of the previous page 
curl -s -H "X-Partner-Key: pk_demo_savanna" \
  "https://accessible-onboarding.vercel.app/api/v1/jobs?limit=10"
GET /api/v1/jobs/{id} X-Partner-Key

One published job: title, description, employer, location, work hours, employment type and accommodations (codes such as step_free, screen_reader, flexible_hours). Drafts and closed jobs are 404. 

curl -s -H "X-Partner-Key: pk_demo_savanna" \
  https://accessible-onboarding.vercel.app/api/v1/jobs/{id}

JobPosting JSON-LD (Level 3)

Every published job is available, with no key, as schema.org JobPosting. The employer gets this address back when they publish (jsonld_url) and in the staff app.

GET /api/v1/jobs/{id}/jobposting.jsonld Public

Content type: application/ld+json. Keys come out in alphabetical order. 

{
  "@context": [
    "https://schema.org",
    { "acc": "https://accessible-onboarding.vercel.app/ns/accommodations#" }
  ],
  "@type": "JobPosting",
  "acc:offers": ["remote_work", "screen_reader", "large_text", "own_device", "flexible_hours"],
  "applicantLocationRequirements": { "@type": "Country", "name": "Ethiopia" },
  "datePosted": "2026-11-14",
  "description": "Build and fix pages on our websites with HTML, CSS and JavaScript. …",
  "employmentType": "FULL_TIME",
  "hiringOrganization": { "@type": "Organization", "name": "Example Co" },
  "jobBenefits": "Supports we offer: remote work; tools and documents that work with screen readers; screen magnification and large-print materials; use of your own assistive device or software; flexible hours and breaks.",
  "jobLocationType": "TELECOMMUTE",
  "title": "Junior Web Developer",
  "workHours": "Mon–Fri, flexible hours"
}
  • Standard properties: title, description, hiringOrganization, datePosted, employmentType (FULL_TIME, PART_TIME, CONTRACTOR, INTERN, TEMPORARY), workHours, and jobLocation with a PostalAddress in Ethiopia. Remote jobs get jobLocationType: TELECOMMUTE and applicantLocationRequirements.
  • Accommodations. schema.org has no property for workplace accommodations, so every JobPosting has both: readable text in jobBenefits (every JobPosting reader understands it), and the codes in acc:offers (so a machine can match them to a person's needs).
  • The @context always names the prefix acc as <PUBLIC_WEB_URL>/ns/accommodations#. That address serves the vocabulary (below).
GET /ns/accommodations Public · CORS *

The vocabulary behind the acc prefix. No key, no token, and Access-Control-Allow-Origin: *, so any site can read it. Content type: application/ld+json. It is a schema.org DefinedTermSet with one DefinedTerm per code (termCode is the code, name the English text also used in jobBenefits), and the property acc:offers.

On the hosted site: https://accessible-onboarding.vercel.app/ns/accommodations 

{
  "@context": {
    "acc": "https://accessible-onboarding.vercel.app/ns/accommodations#",
    "schema": "https://schema.org/",
    "rdf": "http://www.w3.org/1999/02/22-rdf-syntax-ns#",
    "rdfs": "http://www.w3.org/2000/01/rdf-schema#"
  },
  "@graph": [
    {
      "@id": "https://accessible-onboarding.vercel.app/ns/accommodations",
      "@type": "schema:DefinedTermSet",
      "schema:name": "Workplace accommodations",
      "schema:hasDefinedTerm": [
        {
          "@id": "acc:screen_reader",
          "@type": "schema:DefinedTerm",
          "schema:termCode": "screen_reader",
          "schema:name": "tools and documents that work with screen readers"
        }
      ]
    },
    {
      "@id": "acc:offers",
      "@type": "rdf:Property",
      "rdfs:label": "offers",
      "schema:domainIncludes": { "@id": "schema:JobPosting" }
    }
  ]
}

For the operator: set PUBLIC_WEB_URL on the API to the public site (for example https://accessible-onboarding.vercel.app). The acc prefix is built from it. If it is unset, or is localhost outside development, the API logs a WARNING at start.

Accommodation codes

Code Meaning (as written in jobBenefits)
screen_reader tools and documents that work with screen readers
large_text screen magnification and large-print materials
sign_language a sign language interpreter for interviews and meetings
captions captions and written notes for meetings
step_free step-free building access
accessible_toilet an accessible toilet
flexible_hours flexible hours and breaks
remote_work remote work
extra_time extra time for tests and tasks
written_instructions written, plain-language instructions
quiet_space a quiet workspace
own_device use of your own assistive device or software
person_to_help a named support person or mentor

The same codes are the learner's support needs. Learners may also choose other, which employers can't offer and which never matches.

How a job board uses it

  1. Fetch the JSON-LD from your server. (Browsers on other sites are blocked by CORS unless their origin is allowed.)
  2. Store it with your copy of the job.
  3. Put it in the job's page inside <script type="application/ld+json"> so search engines see it.
  4. To match a person's needs: a job is a full match when its acc:offers contains every need the person chose, and a partial match otherwise. This is what the component does on the learner's phone.

Importing JobPostings from other boards and a JobPosting feed are not built yet.

Sign-up, step by step (Level 2)

Use these calls to build your own sign-up screens. (The component makes them for you.) The examples use any POSIX shell (Git Bash on Windows): 

API=https://accessible-onboarding.vercel.app/api/v1
KEY=pk_demo_savanna
POST /api/v1/registrations X-Partner-Key

Step 1. Start. Creates a draft learner and registration and returns a learner token. Keep the token: it is shown only once. Only the signup flow can be started today. 

curl -s -X POST "$API/registrations" -H "X-Partner-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"flow_id":"signup","language":"en","simple_mode":false}'

Response (201)

{
  "registration_id": "3f2a9c4e-…",
  "learner_id": "9a8b7c6d-…",
  "status": "draft",
  "current_step": "welcome",
  "session": { "token": "lt_Q2hhbmdlTWVJc1JhbmRvbQ", "expires_at": "2026-12-15T09:30:00Z" }
}
REG=3f2a9c4e-…     # registration_id
TOKEN=lt_…         # session.token
H=(-H "X-Partner-Key: $KEY" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json")
POST /api/v1/registrations/{id}/consents Learner token

Step 2. Consent. Record that the learner agreed to the data-use screen. (The consent screen itself is not saved as an answer.) The component also records cloud_speech when the learner answers the speech question. 

curl -s -X POST "$API/registrations/$REG/consents" "${H[@]}" \
  -d '{"kind":"data_processing","granted":true,"method":"tap"}'
PUT /api/v1/registrations/{id}/answers/{questionId} Learner token

Step 3. Answers. One PUT per question. base_version is the version of that answer you last saw, or 0 the first time. input_method is typed, voice, choice or partner. The server checks and cleans each answer: text is trimmed, an Ethiopian phone number becomes E.164, a date gets both calendars. An empty value (null, "", []) clears an optional answer. 

curl -s -X PUT "$API/registrations/$REG/answers/full_name" "${H[@]}" \
  -d '{"value":"Abebe Kebede Tadesse","input_method":"typed","base_version":0}'
# → {"question_id":"full_name","value":"Abebe Kebede Tadesse","input_method":"typed","version":1,"updated_at":"…"}

curl -s -X PUT "$API/registrations/$REG/answers/contact_method" "${H[@]}" \
  -d '{"value":"phone","input_method":"choice","base_version":0}'

curl -s -X PUT "$API/registrations/$REG/answers/phone" "${H[@]}" \
  -d '{"value":"0912 345 678","input_method":"typed","base_version":0}'
# → "value":"+251912345678"

curl -s -X PUT "$API/registrations/$REG/answers/dob" "${H[@]}" \
  -d '{"value":{"calendar":"ethiopian","year":2010,"month":1,"day":15},"input_method":"typed","base_version":0}'
# → "value":{"calendar":"ethiopian","ethiopian":{"year":2010,"month":1,"day":15},"iso":"2017-09-25"}

curl -s -X PUT "$API/registrations/$REG/answers/id_route" "${H[@]}" \
  -d '{"value":"fayda","input_method":"choice","base_version":0}'

A broken rule answers 422 with the step's error code on the field value: 

{ "status": 422, "code": "validation_failed", "title": "Validation failed",
  "errors": [ { "field": "value", "code": "phone_invalid" } ] }

Step 4. Conflicts between devices (409)

If you send an old base_version, another device saved first. Nothing is saved, and you get the stored answer in current: 

{ "status": 409, "code": "answer_conflict", "title": "Answer changed on another device",
  "current": { "question_id": "full_name", "value": "Abebe Kebede Tadesse", "input_method": "typed",
               "version": 1, "updated_at": "2026-11-15T09:30:12.418Z" } }

Show current to the person, or adopt it. To overwrite it on purpose, send your value again with "base_version": 1. After submit, every change answers 409 already_submitted.

PUT /api/v1/registrations/{id}/support-request Learner token

Step 5. Support needs (optional). Replaces the learner's support request. Every need must be one of the codes (or other). The needs and the free text are encrypted with AES-256-GCM, so the database holds only bytes. The answer never repeats the needs. share_with records who else the learner allows to see them. 

curl -s -X PUT "$API/registrations/$REG/support-request" "${H[@]}" \
  -d '{"needs":["screen_reader","flexible_hours"],"other_text":"Instructions in writing, please.","share_with":{"courses":true,"employers":false}}'
# → {"status":"saved","updated_at":"…"}
PATCH /api/v1/registrations/{id} Learner token

Step 6. Progress (optional). Save the current step, language or Simple mode, so another device can continue there. Answers 204. 

curl -s -X PATCH "$API/registrations/$REG" "${H[@]}" -d '{"current_step":"support_needs"}'
POST /api/v1/registrations/{id}/submit Learner token

Step 7. Submit. Checks that every required answer on the learner's path is there, then makes the learner registered. For the "I have no ID" route it also creates a referral to the chosen organisation. Submitting twice is safe: you get the same answer. 

curl -s -X POST "$API/registrations/$REG/submit" "${H[@]}" -d '{}'
# → {"status":"registered","learner_id":"9a8b7c6d-…","identity_level":"self_declared"}

Missing required answers come back as 422 with one entry per step, for example {"field":"id_route","code":"required"}.

Step 8. Read it back

GET /registrations/{id} returns every answer with its version (never the support needs). GET /me returns the learner's profile; it is the only place support needs are decrypted, for the learner only. 

curl -s "$API/registrations/$REG" "${H[@]}"
curl -s "$API/me" "${H[@]}"

The sign-up questions

The order and branches come from shared/flows/signup.json. The component and the API read the same file. Only questions on the learner's path count on submit.

Step ID Question Required Values and rules Asked when
welcome Welcome screen – not saved always
consent_data Consent to data use yes recorded with POST …/consents always
full_name Your name, your father's name and your grandfather's name (one field) yes at least 2 characters (too_short) always
contact_method How can we reach you? yes phone, telegram, partner (through an organisation), none always
phone Phone number yes Ethiopian mobile (09…/07…, any common spelling), stored in E.164 (+251…); else phone_invalid contact is phone or telegram
dob Date of birth (Ethiopian or Gregorian calendar) no a real date (date_invalid) always
sex Sex no female, male always
region Region or city no the 12 regions, addis_ababa, dire_dawa, outside_ethiopia always
education Highest education no none, primary, secondary, tvet, degree, postgraduate always
id_route Which ID do you have? yes fayda, kebele_id, refugee_id, unhcr_proof, other_document, none always
id_doc_type Document type yes student_id, birth_certificate, idir_equb_id, kebele_letter, driving_licence, passport, other id_route is other_document
id_upload Photo of the document no JPEG, PNG or WebP, at most 1.5 MB, sent as {"name", "data"} with a data:image/…;base64,… URL. Stored encrypted; only {"name"} is ever returned. id_route is other_document
id_last4 Last 4 characters of the document no exactly 4 letters or digits (last4_invalid) an ID route other than none, except documents kebele_letter and other
referral_partner Which organisation can help you? yes the id of a referral organisation from GET /config id_route is none
referral_contact How can they reach you? yes phone, telegram, in_person id_route is none
support_needs, support_other, support_share What would help you? Anything else? Who may see it? no sent together with PUT …/support-request, not as answers always
check, done Check your answers; Done – not saved always

"Preferred name" is no longer asked. The API field preferred_name still exists and is normally empty.

Identity: what is recorded, and what is not.

Bridge does not verify identity. The learner says which ID they have, and identity is recorded as self_declared (or handled in person through a referral organisation for people with no ID). The last 4 characters of a document are not verification: they are an optional reference that helps staff match a document in person. Real Fayda verification would be OTP or biometric authentication through the national ID programme (NIDP) as a licensed relying party. That is on the roadmap and is not built.

Job applications

POST /api/v1/jobs/{id}/applications Learner token

Apply for a published job. Only a learner who finished signing up can apply (a draft learner gets 403 forbidden). One application per job (409 already_exists the second time). answers are the answers of the job-application flow, keyed by step ID. attach_support_request: true lets the employer of this job read the learner's support needs with this application; each read is audit-logged. 

{
  "answers": {
    "contact_confirm": { "value": "yes", "input_method": "choice" },
    "motivation": { "value": "I like building web pages and I learn fast.", "input_method": "voice" },
    "start_date": { "value": { "calendar": "gregorian", "iso": "2026-12-01" }, "input_method": "typed" },
    "attach_support": { "value": "yes", "input_method": "choice" }
  },
  "attach_support_request": true
}

Learner profile (/me)

Every call needs the partner key and the learner's own token.

Call What it does
GET /api/v1/me Profile, latest registration, identity evidence (only whether the last 4 were given, never the characters), referral and support request.
PATCH /api/v1/me Change own details (only the fields sent). A changed phone number is marked unverified. Before submit, only language and simple_mode may change (409 not_registered otherwise).
GET /api/v1/me/export Download all data stored about the learner as JSON.
DELETE /api/v1/me Delete the learner and everything about them (registrations, answers, identity evidence, referrals, support request, consents, applications, sessions). Answers 204.

Resume on another device

  1. Make a link and a code. POST /api/v1/registrations/{id}/resume-links (learner token, while the registration is a draft) returns a link (<PUBLIC_WEB_URL>/r/<token>) and a short code such as K7M-9P2. Both are single use and valid for 72 hours. With {"send_via":"sms"} they are also texted (SMS is simulated today).
  2. Look it up. POST /api/v1/resume/lookup with {"code":"K7M-9P2"} (or {"token":"…"}) says which check the learner must pass: dob or phone.
  3. Pass the check. POST /api/v1/resume/verify with the code and dob (year, month, day) or phone_last4 returns a new learner token. A mismatch is 401 resume_check_failed with attempts_left; after 5 failures the code is locked (429 too_many_attempts). 
POST /api/v1/resume/verify
{ "code": "K7M-9P2", "phone_last4": "5678" }
# → {"registration_id":"3f2a9c4e-…","session":{"token":"lt_…","expires_at":"…"}}

These calls need the partner key and have the strict rate limit.

Speech

POST /api/v1/speech/transcriptions Learner token

Turns one recorded voice answer into text. Multipart upload with audio (at most 3 MB) and language. The audio is never stored. A cloud provider is used only if the learner's latest cloud_speech consent is yes. Answers {"transcript", "confidence", "provider"}, or 503 speech_unavailable.

POST /api/v1/speech/synthesis X-Partner-Key

Reads fixed interface text aloud as MP3 (at most 600 characters). Never send a learner's own answers here: the component reads those with the device's voice only. Without a speech service configured it answers 503 speech_unavailable, and the component falls back to the device's voice. 

{ "text": "What is your full name?", "language": "en" }

Partner server API (OAuth 2.0)

Your server can read the learners who signed up on your site. It uses OAuth 2.0 client credentials: a client_id and a secret, swapped for a 1-hour token with the scope learners:read. Never call it from a browser.

Step 1. Get a client ID and secret (operator)

The Bridge operator gives your partner a client ID and secret. The secret is stored only as a SHA-256 hash, so it is handed over once. Make it with openssl rand -base64 32. 

UPDATE partners
SET client_id = 'your-server',
    client_secret_hash = sha256(convert_to('<a long random secret>', 'UTF8'))
WHERE publishable_key = 'pk_…';
POST /api/v1/oauth/token Client credentials

Step 2. Get a token. Form-encoded. Swap your client_id and client_secret for a partner token (pt_…) that lasts one hour. 

curl -s -X POST "$API/oauth/token" \
  -d grant_type=client_credentials -d client_id=your-server \
  -d client_secret="$CLIENT_SECRET" -d scope=learners:read

Response (200)

{ "access_token": "pt_…", "token_type": "Bearer", "expires_in": 3600, "scope": "learners:read" }

Errors use the OAuth shape: 400 {"error": "invalid_request"}, "unsupported_grant_type" or "invalid_scope"; 401 {"error": "invalid_client"}.

GET /api/v1/partner-api/learners Bearer pt_… · learners:read

Step 3. List your learners. Only learners of your partner who finished signing up, newest first. limit is 1–200 (default 50). cursor is accepted but paging isn't built yet (next_cursor is always null), so use updated_since to fetch only changes since your last call. A token without the scope gets 403 insufficient_scope. 

curl -s -H "Authorization: Bearer $PT" \
  "$API/partner-api/learners?updated_since=2026-11-15T00:00:00Z&limit=50"

Response (200)

{
  "items": [
    {
      "learner_id": "9a8b7c6d-…",
      "full_name": "Abebe Kebede Tadesse",
      "preferred_name": "",
      "language": "am",
      "status": "registered",
      "identity_level": "self_declared",
      "contact": { "method": "phone", "phone": "+251912345678", "verified": false },
      "registered_at": "2026-11-15T09:40:02Z"
    }
  ],
  "next_cursor": null
}

Local development

When you run Bridge on your own computer:

  • API base: http://localhost:8080/api/v1
  • Swagger UI: http://localhost:8080/api/docs
  • Development web server: http://localhost:5173 (it forwards /api and /ns to http://localhost:8080)
  • Demo partner keys from seed: pk_demo_savanna, pk_demo_jobboard (platforms) and pk_demo_aaapd (referral organisation). They allow http://localhost:5173, http://127.0.0.1:5173, http://localhost:4173, http://127.0.0.1:4173, http://localhost:8080 and http://localhost:8081.
  • Set PUBLIC_WEB_URL=http://localhost:5173 in development. Before deploying, set it to your public site.
