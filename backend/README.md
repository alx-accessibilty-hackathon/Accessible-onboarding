# Backend (Go)

Clean architecture, using the same layout as the G6-WorryMate backend. Gin for HTTP, PostgreSQL (pgx) for data, [sqlc](https://docs.sqlc.dev) to generate the database code, and [goose](https://github.com/pressly/goose)-format migrations.

## Layout

```text
backend/
├── main.go                  wires everything: config → repositories → use cases → controllers → router
├── Config/config.go         every environment variable, read once (nothing else calls os.Getenv)
├── Domain/
│   ├── entities.go          plain structs and shared values (no JSON tags, no database code)
│   └── interfaces.go        use case, repository and service interfaces
├── Usecase/                 business rules and permission checks; depends only on Domain interfaces
├── Repository/              repositories: call sqlc's generated methods, map rows to Domain entities
│   ├── queries/             the SQL you write, one file per table group (input to sqlc)
│   └── sqlc/                generated by sqlc: never edit by hand
├── Infrastructure/          middleware (incl. rate limits) and outside services (security, speech-to-text, SMS)
├── Delivery/
│   ├── Controllers/         HTTP handlers + request/response DTOs (<area>_dto.go)
│   ├── Routers/router.go    every route in one place
│   └── mocks/               generated mocks for tests (mockery)
├── migrations/              goose migrations (also the schema sqlc reads)
└── sqlc.yaml                sqlc settings
```

**Dependency rule:** Controllers → Usecase → Domain ← Repository / Infrastructure. A use case never imports `gin` or `pgx`.

## Conventions

- **IDs are `uuid.UUID`** everywhere: Domain, DTOs and sqlc code.
  - The only string identifiers are the flow file IDs (`"signup"`) and question/step IDs (`"phone"`).
  - Read an ID from the path with `uuidParam(c, "id")`, which answers `400 invalid_id` on a bad value.
- **DTOs live only in `Delivery/Controllers/<area>_dto.go`.** Domain entities have no JSON tags.
  - Each DTO file holds the request structs (with `binding` rules), the response structs, and mapping helpers: `toXDTO(domain)` for responses and `req.toDomain()` for requests.
- **Requests are bound with `bindJSON`, `bindQuery` or `bindForm`** (in `common_dto.go`). They answer for you:
  - **400 `invalid_request`** for unreadable JSON
  - **422 `validation_failed`** with `errors: [{field, code}]`, using JSON field names and codes such as `required`, `too_long` and `invalid_choice`

  A handler starts like this:

  ```go
  var req CreateRegistrationRequest
  if !bindJSON(c, &req) {
      return
  }
  ```

- **Errors:** repositories and use cases return `domain.Err…` sentinels. Controllers never compare error strings.
- **Lists** return `ListResponse[T]` (`items`, `next_cursor`).
- **Config:** add new settings to `Config/config.go` and `.env.example`, then pass the value in from `main.go`.

## Run

```bash
cp .env.example .env          # set DATABASE_URL, DATA_ENCRYPTION_KEY, CODE_HASH_KEY (openssl rand -base64 32)
go run . migrate              # apply every migration (embedded in the binary)
go run . seed --if-empty      # demo partners, staff accounts and 6 jobs; prints the keys and accounts
go run .                      # the API on http://localhost:8080 (health: /health, docs: /api/docs)
go test ./...
```

- **Staff accounts** (password from `SEED_STAFF_PASSWORD`, or a random one that is printed):

  - `staff@aaapd.example`, `staff@savanna.example` (partner staff)
  - `support@example.org`, `admin@example.org`

- **Jobs:** 6 published demo jobs.
- **Simulated SMS inbox** (`APP_ENV=dev`): `GET /api/v1/dev/messages` lists the SMS still `queued`. With `SMS_PROVIDER=console` (the default) that is every SMS. With `SMS_PROVIDER=smsethiopia` and `SMSETHIOPIA_API_KEY` they are really sent (`Infrastructure/message_service.go`, in the background, results in `messages_outbox` and the log as `[SMS SENT - SMSETHIOPIA]` / `[SMS FAILED - SMSETHIOPIA]`); which SMS a learner gets is in `Usecase/notify.go`.

**Everything with Docker** (from the repository root): copy `.env.example` to `.env`, fill in the keys, run `docker compose up --build`, then open http://localhost:8081. The API container runs `migrate`, `seed --if-empty` and `serve`.

Use Go 1.24. If `go get` tries to download a newer toolchain, run it with `GOTOOLCHAIN=local`.

**Database tests.** The repository tests and the end-to-end HTTP tests (`e2e_test.go`) run the real SQL against PostgreSQL. They are skipped unless `TEST_DATABASE_URL` is set. Each test creates its own schema, applies every migration and drops the schema afterwards, so any empty database works:

```bash
TEST_DATABASE_URL="postgres://bridge:bridge@localhost:5432/bridge?sslmode=disable" go test ./...
```

**Live QA suite.** `qa_test.go` calls a **running** API over HTTP and checks the results in that API's database (`DATABASE_URL`, from the environment or `.env`), then deletes the rows it created. It is skipped unless `QA_BASE_URL` is set, so `go test ./...` and CI never run it. Start the API, then:

```bash
QA_BASE_URL=http://localhost:8080 go test -run TestCompleteQAExecution -v .
```

If nothing answers at `QA_BASE_URL/health`, it stops at once with that message. Point it only at a database you may write to (not the team's shared one during a demo).

## Database code with sqlc

sqlc reads the migrations (the schema) and the queries in `Repository/queries/`, then writes type-safe Go into `Repository/sqlc/`. Repositories call that code; nothing else does.

1. **Table change:** add a new migration in `migrations/`, for example `00002_registration.sql`, with `-- +goose Up` and `-- +goose Down` sections. Never edit a merged migration.
2. **Query:** write it in `Repository/queries/<area>.sql` under a name line: `-- name: GetLearner :one` (`:one` returns one row, `:many` a list, `:exec` nothing).
3. **Generate:** run `sqlc generate` from `backend/`. The new method appears on `sqlc.Queries`.
4. **Repository:** call `r.Q.GetLearner(ctx, …)`, turn `pgx.ErrNoRows` into `domain.ErrNotFound`, and map the row to a Domain entity. `partner_repository.go` is the example.
5. **Commit:** commit the generated files too. CI runs `sqlc diff` and fails if they are out of date.

Generated types:
- `uuid` becomes `uuid.UUID`
- `timestamptz` and `date` become `time.Time`
- `jsonb` becomes `json.RawMessage`
- nullable columns become pointers, for example `*string`

**Transactions** (when one action writes several tables):

```go
tx, err := r.DB.Begin(ctx)
defer tx.Rollback(ctx)
q := r.Q.WithTx(tx)
// q.CreateX(...); q.UpdateY(...)
return tx.Commit(ctx)
```

**Install sqlc 1.31.1:**
- **Windows:** download `sqlc_1.31.1_windows_amd64.zip` from https://github.com/sqlc-dev/sqlc/releases/tag/v1.31.1 and put `sqlc.exe` on your PATH.
- **macOS:** `brew install sqlc`.
- **Docker:** `docker run --rm -v "${PWD}:/src" -w /src sqlc/sqlc:1.31.1 generate`.

## Migrations

The files follow goose's format and are embedded in the binary. `go run . migrate` applies them (goose as a library). Never edit a merged migration; add a new one.

## Adding an endpoint

1. **Domain:** add the method to the interface in `interfaces.go`, and any new entity to `entities.go`.
2. **Repository:** add the query and call the generated method (see "Database code with sqlc").
3. **Usecase:** implement the rule, including the permission check.
4. **Controller:** bind the DTO, call the use case, return JSON (errors use `ErrorResponse`).
5. **Router:** the route already exists for Must endpoints; it returns 501 until step 4 is done.
6. **Test:** regenerate the mocks and write the use case and controller tests.

   ```bash
   mockery --dir Domain --all --output Delivery/mocks
   ```

7. **Contract:** add the endpoint, with an example, to `../api/openapi.yaml`.

## Status

**Sign-in works end to end:**
- the partner key and allowed origin (`PartnerKeyMiddleware`)
- learner tokens (`lt_`, from `POST /registrations` or resume verify; 30 days, sliding)
- staff tokens (`st_`, `POST /auth/staff/login`, 12 hours) with roles
- partner-server tokens (`pt_`, OAuth client credentials, 1 hour) with scopes

Only SHA-256 hashes of tokens are stored. Staff passwords use bcrypt.

The partner key may also come from the query string (`?key=` or `?partner_key=`) when the `X-Partner-Key` header is missing; the allowed-origin check is the same.

**Built:**
- **Registrations:** answers, progress, submit, the support request (encrypted) and consents
- **Continue on another device:** resume links, lookup and verify
- **Sign in again with a code:** `GET /me/sign-in-code` (made the first time, for registered learners only) and `POST /me/sign-in-code` (a new one). `POST /resume/lookup` and `/verify` take it too: 8 letters and digits is a sign-in code (`Usecase/signin_codes.go`, table `signin_codes`, migration 00008), 6 is a resume code. The answer has `kind: sign_in` and the widget opens the profile. Reusable; checked against the learner's date of birth or phone; 5 wrong checks lock it for 15 minutes; only for learners of the key's partner
- **The learner's own data (`/me`):** see, change and delete (below)
- **Jobs:** public jobs, JobPosting JSON-LD, the JSON-LD vocabulary of its `acc` prefix (`GET /ns/accommodations`, public, outside `/api/v1` so that `PUBLIC_WEB_URL/ns/accommodations` can be forwarded to it), employer jobs, applications, and the employer's view of the applications to their jobs
- **Start-up check:** `serve` logs a `WARNING` when `PUBLIC_WEB_URL` is not set, or is a localhost address outside `APP_ENV=dev` (`Config.PublicWebURLProblem`): JobPosting and resume links are built from it
- **Partner staff:** the consent code, the referral queue and the trusted referral (vouch code, `Usecase/vouch_usecase.go`; the learner enters it at `POST /me/vouch`)
- **Self-service partners:** `POST /partners` (public, 30 an hour per IP, `PARTNER_SIGNUP_DAILY_LIMIT` a day, `PARTNER_SELF_SERVICE=off` turns it off; `Usecase/partner_signup.go`). It checks the form, makes `pk_live_` + 128 random bits, a `client_id` and a secret (only its SHA-256 hash is stored, the secret is in the answer only) and inserts the partner (`CreatePartner` in `queries/partners.sql`; a taken slug is `409 already_exists`). The CORS list reloads at once (`infrastructure.AllowedOriginsChanged`), and an unknown origin reloads it at most every 10 seconds, so the new site works straight away. No migration was needed.
- **Platform:** `/config`, speech-to-text (Addis AI, Azure, local, mock), the partner API (list and detail)
- **Read aloud (server voice):** `POST /speech/synthesis` in `Infrastructure/tts.go`. Amharic is read by Addis AI with one fixed voice (`ADDIS_AI_API_KEY`, `ADDIS_AI_VOICE_ID`), then Azure if set up. Each clip is cached under provider + voice + language + SHA-256 of the text, in RAM, on disk (`TTS_CACHE_DIR`) and in the database (`tts_cache`, migration 00006, `Repository/tts_cache_repository.go`): a provider is called once per clip; parallel requests for a new clip share one call; a started call finishes and is stored even if the client leaves; `TTS_DAILY_LIMIT` caps paid calls per day. Logs: `[TTS HIT - RAM|DISK|DB]`, `[TTS MISS - CALLING ADDIS]`, `[TTS MADE - ADDIS]`, `[TTS STORED - …]`, `[TTS WAIT]`, `[TTS LIMIT]`, `[TTS ERROR - …]`. At start-up the API logs Addis AI's Amharic voices and warns if `ADDIS_AI_VOICE_ID` isn't available. Before an Amharic text is sent (and cached), `Infrastructure/tts_text.go` turns it into plain Amharic words (numbers and times as words, English words and acronyms in Amharic letters, no symbols or trailing punctuation); nothing Amharic left → `422 not_amharic`. `go run . tts-clear` empties the database and folder cache (restart the API after it).
- **Running it:** `migrate` and `seed`, the dev SMS inbox, and Docker

### Learner profile, referral queue, employer applications

Errors use the usual shape `{status, code, title, errors: [{field, code}]}`.

**`GET /api/v1/me`** (partner key + learner token): the learner's own data. The support request is decrypted here only, because it is theirs.

```json
{ "learner_id": "…", "registration_id": "…", "status": "registered",
  "full_name": "Abebe Kebede", "preferred_name": "", "contact_method": "phone", "phone": "+251912345678",
  "dob": { "iso": "2017-09-25", "calendar": "ethiopian" }, "language": "am", "simple_mode": false,
  "identity": { "route": "other_document", "doc_type": "kebele_letter", "level": "self_declared", "has_last4": false },
  "support": { "needs": ["screen_reader"], "other_text": "", "share_with": { "courses": false, "employers": true } },
  "referral": { "partner_name": "AAAPD", "status": "requested", "contact_preference": "in_person" },
  "registered_at": "2026-11-15T09:32:02Z" }
```

`dob`, `identity`, `support`, `referral` and `registered_at` are `null` when there is nothing.

**`PATCH /api/v1/me`**: only the fields sent change: `full_name`, `preferred_name`, `contact_method`, `phone`, `dob` (same value as the sign-up answer; `null` clears it), `language`, `simple_mode`. Each field is checked with the rule of the sign-up step of the same name (`preferred_name`, which the sign-up no longer asks, is only trimmed and limited to 100 characters, `too_long`), and errors name the field (`{"field":"phone","code":"phone_invalid"}`). Contact by `partner` or `none` clears the stored phone, including the phone answer saved at sign-up. Contact by `phone` or `telegram` with no phone stored or sent is `422 {field: "phone", code: "required"}`. Before submit, only `language` and `simple_mode` may change; anything else is `409 not_registered`. Answers `200` with the `GET /me` body. Support needs are changed with `PUT /registrations/{id}/support-request`.

**`DELETE /api/v1/me`**: `204`. In one transaction: deletes the learner (registrations, answers, resume tokens, identity evidence, referrals, the support request, consents, applications and verification codes cascade), deletes their sessions (and staff sessions acting for them), and writes an `audit_log` row (`learner`, `learner.deleted`, target `learner`, no personal data). The token stops working (`401`).

**`GET /api/v1/partner/referrals`** (staff token, role `partner_staff`): referrals to the staff member's own organisation, newest first: `{ "items": [{ "id", "status", "contact_preference", "created_at", "learner": { "learner_id", "full_name", "preferred_name", "contact_method", "phone", "language" } }], "next_cursor": null }`.

**`PATCH /api/v1/partner/referrals/{id}`** (`partner_staff`), body `{ "status": "in_progress" | "closed" }`: `200` with one item. Another organisation's referral is `404`.

**`GET /api/v1/employer/jobs/{id}/applications`** (staff token, role `employer`): applications to the employer's own job, newest first: `{ "items": [{ "id", "status", "created_at", "answers", "attach_support", "applicant": { "full_name", "preferred_name", "contact_method", "phone", "language" }, "support": { "needs", "other_text" } | null }], "next_cursor": null }`. `support` is filled only when the applicant attached it to that application, and each decrypt writes an `audit_log` row (`staff`, `support_request.read`, target `learner`, meta `{"job_id": …}`). Another employer's job is `404`.

**Date answers** may leave out `iso`: the API computes it from the `ethiopian` part or from a flat `{ "calendar", "year", "month", "day" }`, and stores `{ calendar, ethiopian?, iso }`.
